# Hati — Group Bill Splitting App (Build Spec)

> **Working name:** "Hati" (Filipino for *split/half*). Rename freely.
> **Audience for this document:** an AI coding agent (or developer) building v1 from scratch. Follow it literally; where something is not specified, choose the simplest option consistent with this spec and note the decision in `DECISIONS.md`.

---

## 1. Product summary

Hati lets friends create **groups**, invite others via a **shareable link**, and log **shared bills** inside a group. One person pays up front (the *payer*); the bill is split among selected group members using one of four split modes. Each member then settles their share with the payer outside the app (GCash, Maya, bank), and the payer confirms receipt in-app.

### Reference scenario (use this as the primary acceptance walkthrough)

1. Bea creates a group **"Tagaytay Staycation"** and shares the invite link in the barkada group chat.
2. Carlo, Dana, and Eli tap the link, sign up / log in, and land in the group.
3. Bea books the Airbnb for **₱12,500** and adds a bill: *"Airbnb – 2 nights"*, paid by Bea, split **equally** among all 4 members, with a screenshot of the booking attached.
4. Each member sees they owe Bea **₱3,125**. Bea's own share is auto-settled.
5. Carlo opens the bill, taps **Settle up**, sees Bea's GCash QR and number, pays in GCash, returns and taps **I've paid** (optionally attaching the GCash receipt screenshot).
6. Bea gets a push notification, reviews, and taps **Confirm received**. Carlo's share becomes *Settled*.
7. Later, Dana adds a bill for groceries using **itemized** split. The group activity feed shows both bills, payments, and comments.

## 2. Scope

### In scope (v1)
- Email + password auth (Supabase Auth), with email verification and password reset.
- User profile: display name, avatar, and **payment methods** (GCash / Maya / bank, with optional QR image).
- Groups: create, rename, set photo, archive; roles `owner`, `admin`, `member`.
- Invite via **shareable link** (no approval step — anyone with a valid link joins).
- Bills with a **single payer**, split modes: **equal, exact amounts, percentages, shares (weights), itemized**.
- **Per-bill balances**: every bill is settled independently (no cross-bill debt simplification).
- Settlement flow: debtor marks paid → payer confirms (or rejects).
- **Receipt photo upload** on bills and on payments.
- **Activity feed** per group + **comments** on bills.
- **Recurring bills** (e.g. monthly rent, subscriptions).
- **Push notifications** (FCM) for key events.
- **Currency: PHP only.**

### Out of scope (v1)
- In-app money movement / payment gateways.
- Multi-currency, exchange rates.
- Debt simplification across bills.
- Multiple payers on a single bill.
- Social login, phone OTP, magic links.
- Web client (Supabase schema should not preclude one later).
- Offline-first sync (show cached data read-only when offline; writes require connectivity).

## 4. Architecture

### 4.1 Principles
- **Money is stored as integer centavos** (`bigint`) everywhere. Never use floating point for money, on client or server.
- **The server is the source of truth for split validity.** The client computes a live preview; bills are created/edited via Postgres RPC functions that re-validate and write atomically.
- **Row Level Security on every table.** Clients talk to Supabase directly; there is no custom API server. Privileged operations go through `security definer` RPCs or Edge Functions.
- **Activity feed and notifications are generated by database triggers**, not by the client, so they can't be skipped or spoofed.

All tables have `id uuid primary key default gen_random_uuid()`, `created_at timestamptz default now()`, and `updated_at` where rows are mutable (maintained by trigger). Money columns are `bigint` centavos with `check (x >= 0)`.

### 5.2 Storage buckets (all private)
`avatars`, `group-photos`, `payment-qr`, `bill-receipts`, `payment-proofs`. Access via signed URLs. Storage RLS: a user may read an object if they share a group with the owner (avatars, payment-qr) or are an active member of the object's group (receipts, proofs). Paths are prefixed with the scoping id so policies can parse them.

### 5.3 Activity event types
`group_created`, `member_joined`, `member_left`, `member_removed`, `bill_created`, `bill_edited`, `bill_voided`, `payment_marked`, `payment_confirmed`, `payment_rejected`, `bill_settled`, `comment_added`, `recurring_created`, `recurring_generated`.

### 5.4 Row Level Security (summary)
Helper: `is_group_member(gid uuid) returns boolean` — `security definer`, checks `group_members` where `left_at is null` and `user_id = auth.uid()`.

| Table | Select | Insert/Update/Delete |
|---|---|---|
| profiles | self, or anyone sharing a group | self only |
| payment_methods | self, or anyone sharing a group | self only |
| groups | members | via RPC; update by owner/admin |
| group_members | members of that group | via RPC only |
| group_invites | owner/admin of group | owner/admin |
| bills, bill_shares, bill_items, bill_item_assignees | group members | via RPC only |
| payments | group members | via RPC only |
| bill_attachments | group members | insert by members; delete by uploader or bill creator |
| comments | group members | insert by members; update/delete own |
| activity_events | group members | triggers only (no client writes) |
| recurring_bills | group members | creator or owner/admin |
| device_tokens, notifications, notification_prefs | self | self (notifications: update `read_at` only) |

Former members (`left_at` not null) keep read access to bills they participate in (via `bill_shares.user_id = auth.uid()`), but not to the rest of the group.

## 6. Split engine

Implement **once in pure Dart** (`lib/core/split/`) for live previews **and once in PL/pgSQL** inside the RPCs for validation. Both must produce identical results; share a JSON test-vector file (`supabase/tests/split_vectors.json`) used by both test suites.

### 6.1 Inputs / outputs
- Input: `total` (centavos), ordered `participants` (user ids, ordered by `group_members.joined_at`, then `user_id`), mode-specific inputs.
- Output: map `user_id → amount` (centavos). **Invariant: sum of amounts == total.**

### 6.2 Remainder rule (all modes)
Compute each participant's exact fractional share, floor to centavos, then distribute the leftover centavos **one each** using the **largest remainder method**; ties broken by participant order. This is deterministic and never off by more than ₱0.01 per person.

### 6.3 Modes
| Mode | Input | Rule / validation |
|---|---|---|
| `equal` | selected participants | `total / n`, remainder rule. ≥1 participant. |
| `exact` | amount per participant | Sum must equal total exactly. UI shows "₱X left to assign". |
| `percent` | percent per participant (up to 2 decimals) | Must sum to 100.00. Amount = total × pct, remainder rule. |
| `shares` | positive weight per participant (decimals allowed, e.g. 0.5) | Amount = total × w / Σw, remainder rule. |
| `itemized` | items (name, amount, assignees) + extras | Each item split equally among its assignees (remainder rule per item). Subtotal = Σ items. Then `service_charge` and `tax` are added and `discount` subtracted **proportionally to each person's item subtotal** (remainder rule). `total = subtotal + service_charge + tax − discount` and must match `bills.total_amount`. Every item needs ≥1 assignee. |

The payer may or may not be a participant. If the payer is a participant, their `bill_share` is created with `status = 'settled'`.

### 6.4 Required unit tests (minimum)
- ₱100.00 equal among 3 → 33.34 / 33.33 / 33.33 (first by order gets the extra centavo).
- ₱12,500 equal among 4 → 3,125 each.
- Percent 33.33 / 33.33 / 33.34 of ₱1,000.
- Shares 2 : 1 : 1 of ₱1,000 → 500 / 250 / 250.
- Itemized with 10% service charge and a ₱50 discount; sum equals total.
- Rejects: exact amounts not summing, percents ≠ 100, zero weights, item with no assignees, zero participants.

## 7. Server functions (Postgres RPC, `security definer`, check `auth.uid()`)

| Function | Purpose |
|---|---|
| `create_group(name, photo_path)` | Inserts group + owner membership, emits `group_created`. |
| `create_invite(group_id, expires_in_hours?, max_uses?)` | Owner/admin only. Returns token. |
| `get_invite_preview(token)` | Returns group name, photo, member count, inviter name — callable by any authenticated user; used on the join screen. |
| `join_group(token)` | Validates token (not revoked/expired/over limit), inserts membership (or clears `left_at` for rejoin), increments `use_count`, emits `member_joined`. Idempotent for existing members. |
| `leave_group(group_id)` | Blocked if caller has any `unpaid`/`pending_confirmation` shares **or** is payer on any bill with unsettled shares. Owner must transfer ownership first unless last member. |
| `remove_member(group_id, user_id)` | Owner/admin; same outstanding-balance block. |
| `create_bill(payload jsonb)` | Validates membership of payer/participants, runs split, inserts bill + shares (+ items), emits `bill_created`. Returns bill id. |
| `update_bill(bill_id, payload jsonb)` | Creator or payer only. **Allowed only while no payment on the bill is `pending` or `confirmed`.** Recomputes shares. Emits `bill_edited`. |
| `void_bill(bill_id, reason)` | Creator, payer, or owner/admin. Allowed only if no payment is `confirmed`; pending payments are auto-rejected. Sets `status='void'`. |
| `mark_share_paid(bill_share_id, method, reference_no, proof_path)` | Debtor only; share must be `unpaid`. Creates `payments` row (`pending`), sets share `pending_confirmation`. |
| `confirm_payment(payment_id)` | Bill payer only. Payment → `confirmed`, share → `settled`. If all shares settled → bill `settled` + `bill_settled` event. |
| `reject_payment(payment_id, reason)` | Bill payer only. Payment → `rejected`, share → `unpaid`. |
| `record_payment_received(bill_share_id, method)` | Payer only — shortcut for cash handed over in person; creates a confirmed payment directly. |
| `get_my_balances()` | Per group: total owed by me, total owed to me (sums of open shares). Powers the home screen. |

### 7.1 Edge Functions
- **`send-push`** — Invoked by a Database Webhook on `notifications` insert. Looks up `device_tokens` and `notification_prefs`, sends via FCM HTTP v1 (service account in Supabase secrets), sets `pushed_at`, deletes tokens FCM reports as unregistered.
- **`generate-recurring-bills`** — Invoked by `pg_cron` daily at **06:00 Asia/Manila** (`0 22 * * *` UTC). For each non-paused template with `next_run_on <= today` and (`ends_on` null or ≥ today): calls the same bill-creation logic (skipping participants who have left the group; if the payer has left, pause the template and notify admins), emits `recurring_generated`, advances `next_run_on`. Must be idempotent per `(template_id, run date)` — add a unique index on `bills(recurring_template_id, bill_date)`.

### 7.2 Notification triggers
A trigger on `activity_events` insert fans out `notifications` rows:

| Event | Recipients | Example copy |
|---|---|---|
| `bill_created` / `recurring_generated` | participants except actor | "Bea added *Airbnb – 2 nights*. You owe ₱3,125." |
| `payment_marked` | bill payer | "Carlo marked ₱3,125 as paid for *Airbnb*. Tap to confirm." |
| `payment_confirmed` | debtor | "Bea confirmed your ₱3,125 payment." |
| `payment_rejected` | debtor | "Bea couldn't find your payment for *Airbnb*: {reason}" |
| `comment_added` | bill participants + payer, except author | "Dana commented on *Groceries*: …" |
| `member_joined` | existing members | "Eli joined Tagaytay Staycation." |
| `bill_edited` / `bill_voided` | participants except actor | "Bea updated *Airbnb*. Your share is now ₱2,500." |

**Reminders:** the daily cron also sends one reminder for shares `unpaid` for 3+ days and again at 7 days (track in `bill_shares.last_reminded_at`). The payer can also tap **Nudge** on a share (rate-limited to once per 24h per share).

## 8. Invite link & deep links

- Link format: `https://hati.app/join/<token>` (replace domain).
- Configure **Android App Links** (`assetlinks.json`) and **iOS Universal Links** (`apple-app-site-association`) on the domain. The domain also serves a tiny fallback page with store badges for users without the app.
- go_router route `/join/:token`:
  1. If not signed in → stash token, go to auth, resume after login/signup.
  2. Call `get_invite_preview` → show **Join group** screen (group photo, name, member avatars, inviter).
  3. On **Join** → `join_group` → navigate to group detail.
  4. Invalid/expired/revoked → friendly error with "Ask for a new link".
- Group settings → **Invite people**: shows the current link with **Copy** and **Share** (system share sheet), expiry/usage options, and **Reset link** (revokes old token, creates new).

## 9. Payment methods & settle-up flow

- Profile → **Payment methods**: add GCash / Maya / bank / other with account name, number, and optional QR image (upload screenshot of their GCash/Maya QR).
- **Settle up** bottom sheet (opened from a share the user owes):
  - Amount owed (large), payer name and avatar, bill title.
  - Tabs/chips for each of the payer's payment methods: QR image (tap to enlarge, long-press to save to gallery), account number with **Copy** button.
  - **Open GCash / Open Maya** button: best-effort launch of the wallet app via `url_launcher` (Android package intent / iOS URL scheme; verify current schemes at build time). If launch fails, fall back to the store listing. Do **not** attempt to prefill amounts — there is no supported public API for that.
  - **I've paid** → form: method, optional reference number, optional proof screenshot → `mark_share_paid`.
- If the payer has no payment methods, show "Bea hasn't added payment details yet" + a **Nudge to add** action, and still allow **I've paid**.

## 11. Design language — Material 3

- `ThemeData(useMaterial3: true, colorScheme: ColorScheme.fromSeed(seedColor: brandSeed))`. Brand seed: a teal/green (e.g. `#00897B`) — reads as "money settled" without looking like any specific wallet brand. On Android 12+ use `dynamic_color` with the seed as fallback.
- Full **light and dark** themes; follow system by default, override in settings.
- Typography: default M3 type scale (Roboto / platform default). Amounts use `displaySmall`/`headlineMedium` with **tabular figures** (`FontFeature.tabularFigures()`).
- Semantic colors (as `ThemeExtension`): `owe` (uses `colorScheme.error` tone), `owed` (tertiary/green tone), `pending` (secondary/amber tone). Never convey status by color alone — always pair with a label or icon.
- Components: `NavigationBar`, `FilledButton` for primary actions, `FilledButton.tonal` for secondary, `SegmentedButton` for split mode, `FilterChip` for bill filters, `Card.filled` for summaries, `ModalBottomSheet` for Settle up, `SearchAnchor` where search exists, `Badge` on notification bell.
- Corner radius and elevation per M3 defaults; 16dp page padding; 8dp spacing grid.
- Money format: `₱12,500.00`; omit `.00` in dense lists only if consistent app-wide (default: always show centavos). Amount inputs use a numeric keypad and parse into centavos.
- Accessibility: min 48dp touch targets, semantics labels on avatar-only chips ("Carlo, owes ₱3,125, unpaid"), supports 200% text scale without clipping.
- Motion: M3 standard easing; container transform from bill card → bill detail.
- Copy tone: friendly, plain, lightly casual ("You're all square!" when everything is settled).

## 12. Edge cases & rules

1. **Editing a bill** is allowed only while no payment is `pending` or `confirmed`. Otherwise UI shows "Void and recreate" guidance.
2. **Voiding** is blocked once any payment is `confirmed`.
3. **Leaving/removing** a member is blocked while they have unsettled shares as debtor or payer; show exactly which bills block it.
4. **Payer not a participant** (e.g. paying on behalf of others) is supported.
5. **Single-participant bill** where participant == payer is allowed (records an expense, no debt).
6. **Recurring bill participants who left** are skipped; if none remain, pause template and notify creator.
7. **Monthly anchor day 31** in a 30-day month → last day of the month.
8. **Deleted accounts**: profile is anonymized to "Deleted user"; blocked if the user has unsettled shares.
9. **Duplicate taps** on mark-paid/confirm must be idempotent (RPC checks current status).
10. **Max amount** per bill: ₱10,000,000.00 (validation on client and server).
11. **Image uploads**: max 5 attachments per bill, 1 proof per payment, compressed client-side; show upload progress; bill save waits for uploads.

## 14. Acceptance criteria (v1 done when…)

- The reference scenario in §1 works end-to-end on a physical Android and iOS device, including the invite link opening the installed app.
- For every split mode, the sum of shares equals the bill total in all test vectors, and Dart and SQL results match exactly.
- A user who is not a group member cannot read any of that group's rows or storage objects (verified by RLS tests).
- A debtor cannot confirm their own payment; only the bill's payer can.
- Recurring bills generate exactly once per period, even if the cron job runs twice.
- Push notifications arrive for: new bill, payment marked, payment confirmed/rejected, new comment.
- No floating-point arithmetic is used for money anywhere in the codebase (lint or grep check in CI).
